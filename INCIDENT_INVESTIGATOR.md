# Evidence-Driven Autonomous Incident Investigator

An agent that investigates injected infrastructure faults in a live, real (not simulated) Docker-Compose deployment of the fraud-detection pipeline in this repo (Kafka + two Go services + a 3-node Redis Cluster), using six read-only MCP tools backed by `docker compose`/Prometheus, on a LangGraph state machine. Built on top of the fraud-detection system in this repo as its target — see [README.md](README.md) for that system itself.

Every number below comes from `eval/summary.md` / `eval/results.csv`, generated by `eval/grade.py` and `eval/aggregate.py` from the raw run data in `eval/runs/`. Nothing here is estimated or rounded up. Where a result has a real caveat, it's stated next to the number, not left out.

---

## 1. What it does

```
START -> baseline -> investigate -> [tool_call | conclude]
                          ^              |
                          +--- tool_call -+
```

- **`baseline`**: a deterministic, code-driven sweep (`get_container_state`, `list_recent_changes`, `get_metrics("up")`, `read_config` on every running service, plus a computed peer-config diff) that runs before the model sees anything, free of charge against the tool budget.
- **`investigate`**: the model sees the full evidence log every round and freely decides what to check next or when to conclude — no fixed hypothesis list, no enumerated choices.
- **`conclude`**: the model writes a structured incident report (root cause, confidence, cited evidence). Two rules are enforced in code here, not just prompted:
  - **Corroboration gate**: a self-reported `confirmed` is downgraded to `best_guess` if the cited evidence doesn't span at least 2 distinct tool names.
  - **Budget-exhaustion gate**: a self-reported `confirmed` is downgraded to `best_guess` if the run used its entire 15-call budget. Added this session after finding a real case (`fault4_kaggle-qwen14b_ragon`, from the original 20-row dataset) where a run burned all 15 calls, stayed self-reported `confirmed`, and scored wrong. It has already prevented a repeat: `kaggle-qwen32b (rag=off)`'s false-confidence rate would be 33% on raw self-reported confidence; with this gate applied, it's 0% (see `eval/summary.md`'s downgrade ablation for that environment).

The MCP server (`mcp-server/server.py`) exposes exactly 6 read-only tools: `query_logs`, `get_metrics`, `list_metric_names`, `get_container_state`, `read_config`, `list_recent_changes`. None of them can mutate the stack.

**Model**: `qwen2.5:32b-instruct` (Q4_K_M) served from a Kaggle T4×2 GPU notebook via Ollama, this is the only automated-agent path — NVIDIA, Groq, and a local-Ollama fallback were removed from `agent/run.py` this session in favor of one supported, always-tested path that fails loudly if misconfigured rather than silently defaulting to something untested.

## 3. Threats to validity (read before quoting any number above)

- **`claude-desktop-sonnet5`'s 80%/20% numbers include one documented contamination case.** Fault 6 was injected 4 times in one debugging session; Prometheus retained all 4 attempts' history even though the changelog was rotated before each. Sonnet's run correctly noticed the resulting restart pattern, then explicitly (and wrongly) concluded the real, logged injection was "too late to be the trigger" and invented an organic memory-leak explanation instead. It's kept in the dataset, scored 0, not excluded — removing inconvenient data isn't the point of this project — but it drives this environment's entire false-confidence rate. Full detail in `eval/runs/fault06/fault6_claude-desktop-sonnet5.result.json`'s grading note.
- **`kaggle-qwen32b`'s 0% is mostly a harness bug, not raw model failure.** `agent/graph.py`'s `investigate()` only retries an LLM call when it's truncated (`finish_reason == "length"`); it does not retry when the model returns prose with no tool call at all, silently treating that as "conclude." One run stopped after exactly 1 extra tool call for this reason. A second run's other leg hit an unrelated Kaggle/ngrok tunnel outage mid-call. This is a known, disclosed gap — see `PLAN.md` — deliberately left unpatched until all 3 new faults had run under identical code, so they'd stay comparable to each other.
- **Claude Desktop legs are not a same-scaffold comparison to the automated legs.** They get only the bare trigger string — no `agent/system_prompt.md`, no baseline sweep, no 15-call budget, no downgrade gate. Sonnet and Haiku's numbers reflect an unconstrained chat session, not the same investigator being tested.
- **`claude-desktop-haiku4.5`'s fault-13 row is a failed session, not a real test.** The model never successfully invoked a tool and asked the user for symptoms instead of investigating — recorded honestly as `inconclusive`, not excluded, but it isn't a fair measurement of Haiku's capability on that fault.
- **6 rows remain in `eval/grading_queue.csv`** (5 from this session, 1 pre-existing from the original dataset) pending either a real Claude Desktop transcript export (to verify exact tool-call counts, currently left `null` rather than estimated) or a re-run of the failed Haiku session above.
- **n is small everywhere** — 2 to 5 per environment. Every accuracy number above has a wide confidence interval; see `eval/summary.md` for the Wilson CIs.

## 4. Rigor that's actually been checked, twice

The first working version of this project's own self-description (`trash/What I have now.md`, archived, superseded by this document) was independently, adversarially re-checked and found to have flattered itself in 6 specific ways — every one of them in the direction of looking more complete than it was. That correction is preserved in that file's own §12, because a reviewer's confidence in a self-report should be informed by how it held up under a real check, not just by reading it once.

The same thing happened again this session, on the new results specifically. An independent audit (run adversarially against this session's own work, including two `eval/score_overrides.csv` entries made by the same person who'd be quoting these numbers) found:

- A grading-note text bug that leaked a literal rubric disqualifier phrase into graded text, inflating or deflating a mechanical score depending on direction — found and fixed **three separate times** before it stopped recurring, including once where the stated justification for a manual score override was itself factually wrong (the override's *result* was correct, its *reasoning* wasn't).
- `eval/grade.py` was silently discarding every hand-set `needs_review` flag on a dict merge — a real code bug, not a documentation gap, found by checking whether flagged rows actually reached the human-review queue rather than trusting that they would.
- `eval/aggregate.py` was mislabeling budget-exhaustion downgrades as "corroboration-gate" fires in the published summary.

All three are fixed and re-verified (a second, independent pass confirmed the fixes, then found and closed two more small gaps). The fixes are as much the point of this project as the results are — an agent whose confidence claims are checked in code is only as trustworthy as the pipeline grading it, and that pipeline needed the same kind of check applied to itself.

## 5. What's not built

- No pytest suite for the invariants (budget cap, duplicate-call guard, both downgrade rules) — described and verified manually, not covered by automated tests.
- The eval harness's `-1` score still conflates an honest "inconclusive" with a technical crash/parse failure — a known, disclosed limitation, not fixed this session.
- `eval/grading_queue.csv`'s "blind" human-review rows still leak the rubric's matched answer phrase in `mechanism_hit`/`target_hit` columns — a real bug, not yet fixed.
- Only 1 tool call is acted on per model turn even if the model requests several — a known regression from an earlier rewrite, not restored (doing so mid-sweep would have made the 3 new faults incomparable to each other).
- `eval/llm_judge.py` (Anthropic-API-based semantic grading, a second opinion alongside `grade.py`'s mechanical phrase matching) and a companion Claude Code skill (`eval/grade-fault-investigation-SKILL.md`) are built and unit-tested for data loading, but have not been executed against a live API key — no semantic-grading numbers exist yet.
- No Kubernetes portability check, no retrieval crossover, no per-claim evidence sourcing at the individual-claim level.

Full chronological build log, including every bug found and the reasoning behind every scope decision, is in `PLAN.md`.
