## Responsibility and run lifecycle

`python -m experiments.runner --case NAME [--runs-dir D]` → `run_case`:

1. `AgentConfig.from_env` validates the model settings and records `model_id`/`model_settings` (fails before the stack is touched).
2. `preflight`: one healthy instance per service, the per-project clean-stack marker, Prometheus targets up, raw traffic growing; images, offsets and Redis key counts recorded; then `consume_marker`.
3. Inject the registered script; `fault_is_live`.
4. `python -m agent.run` without `FAULT_*`; `check_agent_artifacts` (result completed and parseable, trace header, no fault metadata, exactly the five tools, agent-visible prompt present, no token-limit cut); `fault_is_live` again.
5. `finally`: `restore_and_wait` (script + target/cluster/broker probe), then `wait_for_growth("enriched_transactions")` — **processing must resume** — and post-run offsets/keys. Any error ⇒ `invalid`; an interrupt is recorded as `interrupted`, cleaned up, and re-raised.

## Limitations

The processing probe proves that some enriched output resumed, not that every record during the fault was reconciled (that is `pipeline_probe`'s job, without faults). Fault liveness is container state; whether a fault is observable to an agent still needs human review. Real GeoIP data was not exercised (needs credentials).

## Why it is easier to follow

`run_case` reads as five numbered steps with one `finally`; Docker inspection lives in small named functions; stack settings and Kafka helpers exist once in `stack.py` instead of three copies.
