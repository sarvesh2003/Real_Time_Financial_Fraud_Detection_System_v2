## Investigation Summary

Initial symptoms observed:

* `get_container_state` showed **redis2** in an `exited` state while every other container in the stack — including its two Redis Cluster peers — had been running uninterrupted for hours (an isolated, single-node anomaly rather than a stack-wide event)
* Once I looked closer, **go-server** was logging repeated `CLUSTERDOWN` warnings on its per-transaction Redis dedup check, and its live transaction-throughput metric had collapsed relative to its prior trend, with zero recovery over 15+ minutes

Investigation path:

1. **get_container_state** — get a whole-stack baseline before chasing any one service — returned all services "Up ~5h" except `redis2` ("Exited (0) 7 minutes ago") — ruled out a stack-wide crash/restart; pointed at redis2 as the anomaly.
2. **list_recent_changes** (window=6h) — check whether this was a deliberate test vs. an organic failure — returned exactly one entry: inject `CHG-1c22e75c` at `2026-09-10T20:10:50Z` — confirmed a deliberate change was made at a timestamp matching redis2's exit; didn't yet say *what* changed.
3. **query_logs(redis2, since=1h)** — see how/why redis2 stopped — returned a clean shutdown: successful BGSAVE, then `SIGTERM`/"User requested shutdown" at `20:10:51`, "Redis is now ready to exit, bye bye" — ruled out a crash, OOM-kill, or corruption; confirmed a deliberate, graceful stop essentially the same second as the fault injection.
4. **query_logs(go-enricher, since=20m)** — check if downstream services felt redis2's absence — returned normal enrichment activity through `20:10:53`, then continuous `failed to dial ... 192.168.241.101:6379: i/o timeout` / `no route to host` starting `20:11:01` — confirmed a downstream consumer immediately lost access to that specific node.
5. **read_config(go-enricher)** — identify what `192.168.241.101` is and how the client is wired — returned `REDIS_CLUSTER_ADDRS=192.168.241.100,.101,.102` — confirmed `.101` = redis2, and that go-enricher uses a cluster-aware client seeded with all three nodes (not a single hardcoded host).
6. **query_logs(go-enricher, since=2m, then since=10m w/ grep)** — check current status — returned zero log lines in the last 2 minutes, with the last error timestamped `20:12:32` — ruled out a crash loop; go-enricher is idle, not erroring, raising the question of whether it simply has no work.
7. **list_metric_names(contains="lag")** + **get_metrics(kafka_consumergroup_lag, window=20m)** — check if the enricher is silently falling behind — returned lag flatlined at 0 on all 3 partitions shortly after redis2's exit — inconclusive alone (0 lag = healthy *or* nothing being produced), which motivated checking the producer directly.
8. **query_logs(python-producer, since=10m)** — check whether new transactions are even being submitted — returned a **100% failure rate** in the sampled window: every send attempt logs `gRPC Error: StatusCode.INTERNAL - Internal Server Error` — confirmed the ingestion entry point is currently rejecting submissions, explaining the flat Kafka lag as "nothing is getting in."
9. **query_logs(go-server, since=15m, grep=error|panic|redis|INTERNAL|fatal)** — find out why go-server rejects requests — returned continuous `WARNING: Some issue with Redis Dedup check: {CLUSTERDOWN The cluster is down}` and dial failures to `192.168.241.101`, non-stop from `20:11:56` onward — confirmed the mechanism: the **whole Redis Cluster**, not just redis2, is reporting itself down for the dedup check.
10. **query_logs(go-server, since=1m)** — confirm this is still happening now, not a historical blip — every line in the last minute was a dedup-check failure — ruled out recovery or intermittency.
11. **list_metric_names(job="go-server")** + **get_metrics(fraud_server_transactions_total, fraud_server_transaction_errors_total, window=30m)** — get an independent, numeric cross-check of the log-based story — returned `transactions_total` growing steadily (~4/sec) until `20:11:19`, then collapsing to roughly a tenth of that rate, while `transaction_errors_total{reason="redis_dedup"}` simultaneously jumps from a flat baseline of 1 to 297-and-climbing — confirmed, via Prometheus (independent of logs), that real throughput dropped at the exact moment dedup errors began.
12. **get_container_state** (2nd call) — check for self-healing or new failures elsewhere — redis2 still exited ("17 minutes ago" now), everything else still healthy — ruled out auto-failover and ruled out a second, unrelated failure.
13. **read_config(redis1)** and **read_config(redis3)** — check whether the surviving nodes are themselves compromised (e.g., memory pressure) — both returned normal live configs (though redis1 caps memory at 5MB/allkeys-lru while redis3 is unbounded/noeviction — a minor config inconsistency, unrelated to this incident) — ruled out the surviving nodes as a contributing cause.

**Root cause (your conclusion):** Fault injection `CHG-1c22e75c` deliberately stopped redis2, which pushed the 3-node Redis Cluster into a `CLUSTERDOWN` state with no self-recovery, and go-server's ingestion path fails transactions when its Redis dedup check errors — so throughput has collapsed and the producer is now seeing sustained `INTERNAL` errors on submission, starving the enricher and the rest of the pipeline of new data.
