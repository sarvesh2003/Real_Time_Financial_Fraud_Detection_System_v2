# LLM Diagnostic Agent — Post-Hoc Evaluation Redesign
## Implementation Plan for Claude Code

> **Purpose:** Build a defensible, interview-ready evaluation layer over the artifacts that already exist in this repository.
>
> **Hard constraint:** Do **not** rerun the diagnostic agent, do **not** generate new fault executions, and do **not** change the schema of existing `*.result.json` or `*.trace.jsonl` artifacts.

---

# 0. Goal

The evaluation system should answer three questions:

1. **Diagnosis quality** — Did the agent identify the actual injected root cause?
2. **Investigation quality** — Did the evidence and investigation justify the diagnosis?
3. **Confidence calibration** — When the agent said `confirmed`, was it actually trustworthy?

Everything else is supporting information.

The desired evaluation flow is:

```text
Existing historical artifacts
        |
        v
Validity gate
        |
        | valid runs only
        v
+----------------------+     +---------------------------+
| Diagnosis Judge      |     | Evidence / Trace Judge    |
|                      |     |                           |
| sees hidden GT       |     | DOES NOT see hidden GT    |
| + final diagnosis    |     | sees diagnosis + trace    |
| + final explanation  |     | + cited evidence          |
+----------+-----------+     +-------------+-------------+
           |                               |
           v                               v
 correct / partial /              evidence support
 incorrect / abstain              causal reasoning
                                  investigation quality
           \                               /
            \                             /
             +-------------+-------------+
                           |
                           v
                 Existing confidence
          confirmed / best_guess / inconclusive
                           |
                           v
                     Final metrics
```

---

# 1. Non-negotiable constraints

Claude Code must follow all of these:

- Use **only existing historical artifacts**.
- Do not rerun the agent.
- Do not rerun fault-injection experiments to create new measurements.
- Do not change the existing artifact schemas.
- Do not rewrite or overwrite historical `*.result.json` or `*.trace.jsonl`.
- Do not overwrite the existing `eval/results.csv`, `eval/summary.md`, or historical grading outputs.
- Do not use the old substring/keyword grader as the primary correctness judge.
- Existing keyword/rubric data may be used for metadata such as mapping a fault to its injection script, but not as the semantic correctness decision.
- Ground truth must ultimately come from the **actual injected fault / injection script**, not from the model output.
- The trace-quality judge must **not receive hidden ground truth**.
- Deterministic facts must be evaluated with code, not an LLM.
- Semantic questions may use an LLM judge.
- Invalid runs must be excluded **before** semantic scoring and metric aggregation.
- Every implementation phase is **test-first**.
- Stop after every phase and report a concise TL;DR before continuing.

# 2. Existing inputs

The evaluator should consume the artifacts already generated by the project.

## 2.1 Per-run result artifact

Typical file:

```text
eval/runs/fault09/<run>.result.json
```

Relevant existing fields include:

```json
{
  "run_id": "...",
  "fault_id": "9",
  "fault_family": "network",
  "fault_name": "latency_injection",
  "env_label": "...",
  "retrieval_mode": "on",

  "status": "completed",

  "root_cause_id": "go-server-network-latency",
  "summary": "go-server is experiencing network latency...",
  "reasoning": "Latency increased while Redis remained healthy...",

  "confidence": "confirmed",
  "model_self_reported_confidence": "confirmed",
  "confidence_was_downgraded": false,
  "downgrade_reason": null,

  "cited_evidence_indices": [15, 19],
  "distinct_supporting_tools": ["get_metrics", "get_container_state"],

  "calls_used": 8,
  "duplicate_calls": 1,
  "tool_errors": 0,
  "hallucinated_tool_calls": 0,

  "wall_clock_s": 240.0,
  "input_tokens_total": 50000,
  "output_tokens_total": 1800
}
```

Do not assume every historical run has every field populated. Missing historical instrumentation must be handled explicitly.

## 2.2 Per-run trace artifact

Typical file:

```text
eval/runs/fault09/<run>.trace.jsonl
```

The trace contains timestamped events such as:

```json
{"event":"tool_call","node":"tool_call","tool_name":"get_metrics","args":{"promql":"..."},"result":"..."}
{"event":"tool_call","node":"tool_call","tool_name":"read_config","args":{"service":"go-server"},"result":"..."}
{"event":"conclusion","node":"conclude","conclusion":{"summary":"...","confidence":"confirmed"}}
```

The trace is the authoritative source for what tools were called and what evidence was actually returned.

## 2.3 Fault metadata / rubric

Existing:

```text
eval/rubric.yaml
```

Use this primarily to map:

```text
fault_id -> family -> injection script
```

Example:

```yaml
fault_id: 9
family: network
script: network/09_latency_injection.sh
```

Do **not** use `mechanism_any_of`, `target_any_of`, or phrase matching as the new semantic correctness grader.

## 2.4 Injection scripts

Existing fault scripts under:

```text
fault-injection/<family>/<fault>.sh
```

These are the source of truth for what was deliberately changed.

Example conceptual ground truth:

```text
Fault 9:
200 ms tc/netem network latency injected on go-server eth0.
```

The semantic diagnosis judge should be grounded in the actual script, not merely the old keyword rubric.

## 2.5 Existing validity artifacts

Reuse the existing validity machinery rather than reimplementing it blindly:

```text
eval/check_contamination.py
eval/validity/
validity_report.md
```

The new evaluator should integrate with the current validity outputs/checks.

# PHASE 1 — Artifact loading + deterministic provenance checks

## Goal

Create a reliable in-memory view of each historical run without changing the existing schema.

Pair each:

```text
*.result.json
```

with its matching:

```text
*.trace.jsonl
```

and expose the existing fields needed by later phases.

## Tests to write first

At minimum test:

1. A result file is paired with the correct trace file.
2. Missing trace is detected and surfaced cleanly.
3. Malformed JSON / JSONL is rejected or marked invalid rather than silently accepted.
4. `run_id` / `fault_id` inconsistencies are detected.
5. `cited_evidence_indices` outside the evidence range are detected.
6. Valid citations can be resolved back to their actual raw evidence/tool output.
7. Missing optional historical fields do not crash the evaluator.
8. Existing input files are never modified.

Use small fixtures derived from the current schema.

## Implementation

Create a loader/helper layer that provides, per run:

```text
result metadata
final diagnosis
final summary/reasoning
confidence fields
full trace events
tool observations/evidence
resolved cited evidence
existing deterministic counters
```

Do not invent missing values.

Use an explicit state such as:

```text
missing
invalid
not_recorded
```

where necessary rather than silently converting unknown values to zero.

## Deterministic evidence-provenance checks

Before any LLM judge sees a run, verify:

```text
- cited evidence index exists
- citation resolves to an actual recorded observation
- citation belongs to this run
- trace is readable
```

This phase is **not** deciding whether evidence semantically supports the diagnosis.

It only establishes that the cited artifact genuinely exists.

## Phase completion criteria

- Tests pass.
- Existing artifacts unchanged.
- A small sample of real historical runs can be loaded.
- Provenance errors are explicit and inspectable.

Then produce TL;DR and STOP.

# PHASE 2 — Validity gate

## Goal

Ensure semantic grading happens only on runs whose experiment is valid enough to interpret.

The correctness judge must not turn invalid experiments into apparently clean measurements.

## Important

Reuse the repository's existing validity logic wherever possible.

Do not replace a working validity check simply to create a new abstraction.

## Tests to write first

Test that:

1. A validity-failing run is excluded from semantic evaluation.
2. A valid run is allowed through.
3. `SKIP` is **not** silently treated as `PASS` where the existing validity design says otherwise.
4. Leakage/context-integrity failures prevent a run from entering headline metrics.
5. The gate produces a clear reason for every exclusion.
6. Metrics cannot accidentally aggregate excluded runs.
7. The number of surviving runs is derived from current artifacts — never hardcoded.

## Implementation

Produce a machine-readable list such as:

```json
{
  "run_id": "...",
  "eligible": false,
  "reasons": [
    "prompt_size_not_clamped",
    "answer_reachable_from_free_context"
  ]
}
```

or equivalent.

Persist only the gate's **output**, not changes to historical artifacts.

## Important historical note

Previous analysis found a much smaller residual subset after exclusions. Do not hardcode any historical count such as `14`.

Recompute eligibility from the repository's current artifacts/checks and report the actual count.

## Phase completion criteria

- Every run has an eligibility decision or explicit unjudgeable state.
- Semantic judges operate only on eligible runs.
- Exclusion reasons are auditable.
- Tests pass.

Then produce TL;DR and STOP.

# PHASE 3 — Semantic Diagnosis Judge

## Goal

Answer:

> Did the agent identify the actual injected root cause?

This is the primary semantic outcome evaluation.

## Judge input

The diagnosis judge may receive:

```text
1. Actual fault-injection ground truth
2. Agent final diagnosis / root-cause claim
3. Agent final summary
4. Agent final reasoning/rationale
```

It should **not need the full tool trace** to decide root-cause semantic correctness.

Do not include the agent confidence label in the correctness decision unless technically unavoidable. Correctness should be judged independently from confidence.

## Ground truth

Use the actual injection script as the authoritative source.

`rubric.yaml` may locate the script, but the old phrase lists are not the new semantic decision mechanism.

## Judge labels

Exactly:

```text
CORRECT
PARTIAL
INCORRECT
ABSTAIN
```

Suggested definitions:

### CORRECT

The agent identifies the injected root-cause mechanism and materially correct affected target/component. Minor wording differences are acceptable.

### PARTIAL

The agent identifies a meaningful part of the correct subsystem/mechanism but misses an important qualifier, target, or causal detail.

### INCORRECT

The agent attributes the incident to the wrong primary cause, contradicts the injected fault, or gives a materially false root cause.

### ABSTAIN

The agent explicitly declines to identify a root cause / reports insufficient evidence without asserting a competing primary diagnosis.

## Structured output

Use strict structured output, for example:

```json
{
  "run_id": "...",
  "label": "CORRECT",
  "reason": "Agent correctly identifies network latency on go-server as the root cause."
}
```

Keep the textual reason short and auditable.

Do not request or persist hidden chain-of-thought from the judge.

A concise justification is sufficient.

## Tests to write first

Test the judge wrapper/parser using fixed mocked responses:

1. CORRECT parses.
2. PARTIAL parses.
3. INCORRECT parses.
4. ABSTAIN parses.
5. Invalid judge output is rejected/retried safely.
6. Judge failures do not silently become `INCORRECT`.
7. The diagnosis judge payload includes ground truth.
8. The diagnosis judge payload does **not** accidentally use legacy keyword matching as the final verdict.
9. Agent confidence is not used as the correctness label.

Where practical, add a few hand-written semantic fixtures:

```text
GT: 200ms network latency on go-server
Prediction: network latency on go-server -> CORRECT

GT: 200ms network latency on go-server
Prediction: generic network issue -> PARTIAL

GT: 200ms network latency on go-server
Prediction: Redis saturation -> INCORRECT

GT: 200ms network latency on go-server
Prediction: insufficient evidence -> ABSTAIN
```

## Phase completion criteria

- Eligible historical runs can be judged.
- Output is structured and traceable by `run_id`.
- Judge errors are explicit.
- No legacy phrase grader is used as the final semantic verdict.
- Tests pass.

Then produce TL;DR and STOP.

# PHASE 4 — Ground-truth-blind Evidence / Trace Judge

## Goal

Answer:

> Given only what the agent actually observed, was its diagnosis justified?

This is deliberately separate from diagnosis correctness.

A diagnosis may be correct by luck while having weak or unsupported evidence.

## Critical rule

**Do not provide the hidden injected ground truth to this judge.**

This avoids hindsight bias.

The trace judge should see:

```text
agent final diagnosis
agent final explanation / rationale
full recorded trace
resolved cited evidence
```

It may also receive deterministic provenance results from Phase 1.

## Dimensions

Evaluate exactly three semantic dimensions:

### A. Evidence support

Question:

> Does the actual evidence collected/cited support the diagnosis being asserted?

Labels:

```text
PASS
PARTIAL
FAIL
```

### B. Causal reasoning

Question:

> Does the final rationale logically connect the observed evidence to the stated root cause without making unsupported causal leaps?

Labels:

```text
PASS
PARTIAL
FAIL
```

### C. Investigation quality

Question:

> Did the agent gather relevant evidence sufficient for the strength of the diagnosis it ultimately made?

Labels:

```text
PASS
PARTIAL
FAIL
```

Do **not** score based on whether it followed one ideal tool sequence.

There can be multiple valid investigation paths.

Do not reward verbosity or number of tool calls merely because the trace "looks sophisticated."

## Evidence provenance requirement

If the agent claims:

```text
"Metric X was 200ms"
```

but the cited/raw tool output does not support that observation, the evidence dimension must not PASS.

The judge should be instructed to base its evaluation only on recorded tool output, not on assertions repeated in the agent's own summary.

## Structured output

Example:

```json
{
  "run_id": "...",
  "evidence_support": "PASS",
  "causal_reasoning": "PASS",
  "investigation_quality": "PARTIAL",
  "reason": "The cited latency evidence supports the diagnosis, but the investigation did not meaningfully rule out a nearby alternative."
}
```

Again: concise justification, not hidden chain-of-thought.

## Tests to write first

At minimum:

1. Hidden ground truth is absent from the trace-judge payload.
2. Valid evidence citations are included.
3. A nonexistent citation cannot produce PASS.
4. A diagnosis unsupported by raw evidence can be marked FAIL even if the diagnosis sounds plausible.
5. A short but sufficient investigation can PASS.
6. A long irrelevant investigation does not automatically PASS.
7. Invalid judge outputs are safely handled.
8. Missing trace/evidence is not silently treated as FAIL; it should become invalid/unjudgeable as appropriate.

## Phase completion criteria

- Diagnosis and investigation quality are independent outputs.
- Hidden GT is provably absent from trace-judge prompts.
- Evidence claims are grounded against actual trace observations.
- Tests pass.

Then produce TL;DR and STOP.

# PHASE 5 — Judge calibration against human labels

## Goal

Demonstrate that the LLM judge is not simply trusted because it is an LLM.

The judge itself must be evaluated.

## Constraint

Do not create new agent runs.

Use a subset of existing **valid** historical runs.

## Human calibration file

Create a simple calibration artifact, for example:

```text
eval/semantic_eval/human_calibration.csv
```

Possible columns:

```text
run_id
human_diagnosis_label
human_evidence_support
human_causal_reasoning
human_investigation_quality
notes
```

Do not alter original result/trace files.

## Human-label workflow

Human labels must be assigned **before looking at the LLM judge result** for that run.

This avoids anchoring the human to the model.

If no completed human calibration file exists yet:

1. Generate the calibration queue/template from eligible runs.
2. Explain exactly what the human needs to label.
3. Do not fabricate calibration numbers.
4. Mark the phase as waiting for human labels.
5. STOP.

After labels exist, calculate judge-vs-human agreement.

## Calibration metrics

For diagnosis labels:

```text
exact agreement
confusion matrix
Cohen's kappa
```

Because `CORRECT / PARTIAL / INCORRECT / ABSTAIN` contains some ordinal structure, weighted kappa may also be reported if implemented carefully and documented.

Do not rely on agreement percentage alone.

For the three PASS/PARTIAL/FAIL trace dimensions, report the same style of agreement separately.

## Tests to write first

Test the calibration calculation itself using fixtures with known expected outputs:

1. Perfect agreement -> agreement 100%, kappa 1.
2. Total disagreement is reflected correctly.
3. Missing labels are excluded explicitly, not silently treated as a category.
4. Confusion-matrix axis ordering is stable.
5. Calibration set is selected only from validity-eligible runs.
6. Human labels are never overwritten automatically.

## Phase completion criteria

Either:

### A. Human labels exist

- Judge agreement metrics computed.
- Disagreements listed for inspection.
- Tests pass.

or:

### B. Human labels do not exist yet

- Calibration queue generated.
- Tests for the calibration pipeline pass.
- No fake judge-reliability claim is made.
- Phase reports "awaiting human labels."

Then produce TL;DR and STOP.

# PHASE 6 — Final metrics and report

## Goal

Aggregate the semantic judgments + existing confidence and deterministic telemetry into a small, defensible metric set.

Do not bring back every legacy metric simply because it already exists.

---

## 6.1 Headline outcome metrics

### Strict diagnosis accuracy

```text
CORRECT / all valid judged runs
```

Report numerator and denominator.

### Partial rate

```text
PARTIAL / all valid judged runs
```

### Incorrect rate

```text
INCORRECT / all valid judged runs
```

### Abstention rate

```text
ABSTAIN / all valid judged runs
```

Do not silently merge PARTIAL into CORRECT.

Do not silently merge ABSTAIN into INCORRECT.

---

## 6.2 Trace-quality metrics

Report:

```text
Evidence-support PASS rate
Causal-reasoning PASS rate
Investigation-quality PASS rate
```

Also keep PARTIAL and FAIL counts available in the report.

These are semantic evaluator outputs, not deterministic truth.

---

## 6.3 Confidence / calibration metrics

Use the agent's already-recorded confidence:

```text
confirmed
best_guess
inconclusive
```

combined with the **new semantic diagnosis label**.

### Coverage

```text
confirmed runs / all valid judged runs
```

### Selective accuracy

```text
CORRECT AND confirmed
---------------------
all confirmed runs
```

### False-confidence exposure

Use:

```text
confirmed AND INCORRECT
-----------------------
all valid judged runs
```

This answers:

> Across incidents, how often did the system emit a strong but wrong diagnosis?

### Error among confirmed diagnoses

Also report:

```text
confirmed AND INCORRECT
-----------------------
all confirmed runs
```

This answers:

> When the system says `confirmed`, how often is it outright wrong?

Do not call PARTIAL fully correct.

If useful, show PARTIAL separately inside confirmed runs.

### Confidence reliability table

Example:

```text
confidence      n      correct      partial      incorrect      abstain
confirmed       ...
best_guess      ...
inconclusive    ...
```

This is the correct calibration view for categorical confidence.

Do **not** add Brier score or ordinary probability ECE because the agent does not emit calibrated numeric probabilities.

---

## 6.4 Statistical uncertainty

For proportion metrics with sufficient meaning, report:

```text
numerator / denominator
point estimate
Wilson 95% confidence interval
```

Wilson intervals are already conceptually present in the project and are suitable for small proportion samples.

Important:

> Wilson does not solve small sample size. It only communicates uncertainty more honestly.

Do not present narrow-sounding conclusions from tiny cells.

---

## 6.5 Deterministic supporting metrics

Keep these as supporting diagnostics, not headline quality metrics:

```text
calls_used
duplicate_calls
tool_errors
hallucinated_tool_calls
wall_clock_s
input_tokens_total
output_tokens_total
cited_baseline_fraction
existing evidence_groundedness
```

These are useful for debugging cost and behavior.

Do not ask an LLM judge to recompute them.

Do not treat `evidence_groundedness` as proof of semantic reasoning quality; the existing implementation is only a narrow numeric-token grounding check.

---

## 6.6 Limited stratification

Using only existing metadata, provide fault-family slices when there is enough data:

```text
Redis
Kafka
Network
Config
```

For each slice, show counts and core metrics.

Do not claim model rankings or retrieval improvements when the historical dataset is confounded.

Do not create new difficulty labels or synthetic slices that are not supported by the existing artifacts.

---

## 6.7 Final report structure

`final_report.md` should be concise and interview-readable:

```text
1. Evaluation population
   - total historical runs discovered
   - excluded by validity gate
   - valid judged runs

2. Diagnosis quality
   - correct / partial / incorrect / abstain
   - Wilson intervals where applicable

3. Investigation quality
   - evidence support
   - causal reasoning
   - investigation quality

4. Confidence reliability
   - coverage
   - selective accuracy
   - false-confidence exposure
   - error among confirmed
   - reliability table

5. Judge calibration
   - human comparison status
   - agreement / confusion matrix / kappa if available

6. Supporting operational metrics
   - calls / tool errors / latency / tokens

7. Fault-family slices

8. Known limitations
```

## Phase completion criteria

- Only validity-eligible runs enter headline metrics.
- Semantic outcome uses the new diagnosis judge, not substring grading.
- Trace judge did not receive GT.
- All metric denominators are explicit.
- Wilson intervals are correct.
- Human calibration status is stated honestly.
- Report does not resurrect withdrawn/invalid legacy headline numbers.
- Tests pass.

Then produce TL;DR and STOP.

# 6. Important methodological decisions to preserve

## A. Outcome correctness and trace quality are different

A run can be:

```text
diagnosis = CORRECT
evidence_support = FAIL
```

That means the agent got the right answer without sufficiently supporting it.

That distinction is valuable and must remain visible.

## B. Ground truth must not leak into trace grading

Diagnosis judge:

```text
SEES ground truth
```

Trace judge:

```text
DOES NOT SEE ground truth
```

This is intentional.

## C. Validity precedes grading

Order:

```text
artifact loading
    ->
validity gate
    ->
semantic judges
    ->
confidence metrics
    ->
final report
```

Never:

```text
judge everything
    ->
mention contamination afterward
```

## D. Human calibration evaluates the judge

The LLM judge is a measurement instrument.

It is not assumed correct merely because it is a stronger model.

## E. Do not overfit to one investigation path

We care whether the agent gathered sufficient relevant evidence and supported its diagnosis.

We do not require:

```text
Tool A -> Tool B -> Tool C
```

as the only accepted path.

---

# 7. Expected interview explanation

A concise explanation should be defensible as:

> I built a post-hoc evaluation layer over controlled fault-injection runs. The validity gate runs first so contaminated or malformed experiments never enter performance metrics. For valid runs, I separate outcome correctness from investigation quality: a semantic diagnosis judge compares the final root-cause claim against the actual injected fault, while a separate ground-truth-blind trace judge checks whether the recorded evidence and causal rationale justify that diagnosis. I calibrate the LLM judge against human-labelled traces rather than treating it as ground truth. Finally, I combine semantic correctness with the agent's existing categorical confidence to measure coverage, selective accuracy, false confidence, and confidence reliability, while tool errors, latency, tokens, and duplicate calls remain deterministic metrics.

---

# 8. Definition of done

The redesign is complete when:

- Existing historical artifacts remain untouched.
- No new agent/fault runs were needed.
- Validity filtering happens before grading.
- Diagnosis correctness is semantically judged against real fault ground truth.
- Evidence/trace grading is performed without hidden ground truth.
- Citation provenance is deterministically checked.
- Judge outputs are structured and auditable.
- Human-judge calibration workflow exists and never fabricates missing labels.
- Final metrics are small, interpretable, and use explicit denominators.
- Wilson intervals are shown for headline proportions.
- Legacy substring grading is no longer the primary correctness signal.
- Final report states limitations honestly.
- Every phase has tests and passes before progressing.
