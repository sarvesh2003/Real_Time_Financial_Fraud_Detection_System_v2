# Reliability audit — 2026-10-07

**Historical snapshot:** this audit describes the repository before the V2 rebuild started on 2026-10-10. Several code defects below have since been changed. Use [README.md](README.md) and [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for current code behavior; the historical performance and evaluation claims remain unverified.

## Verdict

This is a substantial prototype and a useful diagnostic-agent testbed. It is not yet evidence for a production-grade, exactly-once fraud-detection system, or for a reliable autonomous diagnostic agent. The saved 40% diagnosis figure is arithmetically reproducible, but provisional and unsuitable as a general accuracy claim. Do not put the README's throughput, latency, success-rate, or exactly-once claims on a resume until new evidence is captured.

The current V2 pipeline generates labelled synthetic transactions, ingests them over gRPC, enriches them with GeoIP and per-IP counters, and publishes to Kafka. It does not infer fraud from transaction features. `go-enricher/processor.go` copies `IsFraud` from the synthetic input into the output and emits threshold-based log alerts.

- Ran `python -m eval.semantic_eval.metrics`: reproduced **38 discovered, 8 excluded, 30 eligible, 12 correct, 1 partial, 10 incorrect, 7 abstain**. This gate targets the older pooled evaluation; it does not directly declare the newer semantic report invalid, but many of its experiment-design findings still matter to interpretation.
- Checked `docker compose ps -a`: Go server, Kafka, Prometheus, producer, ZooKeeper and Redis exporter were stopped; Redis and three enricher replicas were running. This is a snapshot of the local machine, not evidence that the stack can never start. No services or faults were changed during this audit.

## Highest-impact findings

1. **The pipeline does not provide exactly-once delivery.** `go-server/server.go:74-130` creates a Redis dedup key before Kafka delivery, calls the asynchronous producer, and returns success without a delivery acknowledgment. A Kafka delivery failure can leave a dedup key that makes a retry return “Already processed.” `go-enricher/enricher.go:172-291` mutates Redis fraud state before publishing the enriched event, skips replayed messages as duplicates, and commits consumer offsets after enqueueing output. Thus a failed output delivery can result in missing enriched transactions. Neither Kafka producer config enables transactions or idempotence. The README's exactly-once claims at lines 85 and 181 are unsupported.
2. **The purported two-hour fraud metrics are not a rolling two-hour window.** The Lua script keeps a cumulative `first_seen`, count, total, average and max, and refreshes a 7,200-second TTL on every transaction (`go-enricher/redis_functions.go:44-73,141`). An IP active for days retains old transactions indefinitely. Velocity is total amount divided by time since the first event, while the first transaction's velocity is zero. Names such as `txn_count_2h` are misleading for active IPs.
3. **The agent experiment has material validity gaps.** Eight of 38 historical runs were excluded for confirmed leakage; 12 of the 30 eligible runs have no trace and cannot have their investigation quality checked (`eval/semantic_eval/final_report.md`). Eight eligible runs target transient faults that may have ended before observation. The fault stimulus check cannot run because per-run injection and restore times were not recorded (`eval/validity_report.md`). Twelve Claude Desktop result rows are manually transcribed (`eval/semantic_eval/artifacts.py:37`). The 30-run diagnosis pool mixes the manual desktop runs with automated runs, model environments and harness versions, so 40% should be described only as an uncalibrated result on this historical set.
4. **The judge has not been calibrated.** `eval/semantic_eval/human_calibration.csv` has only a header. The report correctly marks its 12/30 accuracy and 13/18 investigation PASS counts as provisional. Recomputing a number verifies arithmetic, not whether the judge labels are right. The validity gate also detects prompt truncation, zero agent-chosen calls in six local-model runs, non-model-authored text used by the legacy grader, differing tool budgets and record schemas, and an invalid legacy retrieval ranking key.
5. **The 15-call budget and corroboration gate are weaker than they sound.** `agent/graph.py:208-252` gives the agent a free scripted sweep that can supply about 15 observations before any model-chosen action. `agent/graph.py:383-395` counts *distinct cited tool names* toward “confirmed”; it does not verify that cited outputs independently support the conclusion or even succeeded. The semantic trace judge may catch unsupported reasoning afterward, but the live gate itself cannot guarantee grounded confidence. The report shows five incorrect diagnoses among 15 `confirmed` answers (`eval/semantic_eval/final_report.md`).
6. **The load test does not establish end-to-end reliability.** The benchmark generates random users and IPs, so it barely exercises per-user rate limiting or repeated-user fraud metrics; it checks gRPC status, not downstream Kafka counts, duplicate rate, dropped events or fraud-signal accuracy (`load-tests/run_load_tests.sh`, `load-tests/analyze.sh`). The raw benchmark output is absent. It is possible that the historical numbers came from a real test, but the repository cannot substantiate them.
7. **Runtime robustness needs work.** `go-enricher/enricher.go:76-81` logs a MaxMind initialization error and still defers a potentially nil cleanup function; later lookup can dereference nil readers. Bad protobuf or invalid IP input is only logged as “DLQ to do later” (`go-enricher/enricher.go:119-128,300`). The Go services have no tracked tests for these cases. The Compose stack uses a single Kafka broker and three Redis masters with zero replicas (`docker-compose.yaml`), making the infrastructure a demonstration environment rather than a fault-tolerant production deployment.

## What is defensible now

- Built a Go/gRPC → Kafka → Go enrichment pipeline with Redis Cluster state, Prometheus instrumentation, and a synthetic transaction producer. This is an **implemented architecture**, not a verified throughput or fraud-detection result.
- Built a read-only MCP tool server and LangGraph diagnostic agent with a bounded investigation loop, trace recording, and incident-report output.
- Built a fault-injection and semantic-evaluation harness with artifact checks, leakage exclusions, separate diagnosis and evidence judgments, and confidence reporting. This is the strongest AI-engineering aspect of the repository. The current evaluation result is explicitly provisional.

## Repair order and acceptance evidence

1. **Make the claim precise.** Rename/project-frame V2 as a real-time *fraud transaction enrichment and diagnostic-agent testbed*. Remove “production-grade,” “exactly once,” and unverified performance headlines until measured. State clearly that the `is_fraud` label comes from the synthetic producer.
2. **Fix correctness before benchmarks.** Decide whether the target is at-least-once with idempotent downstream behavior or true Kafka transactions. Make ingestion success depend on broker delivery, handle dedup state on failed delivery, and make output publication and offset management safe against retries. Add integration tests that kill Kafka during produce and replay consumer messages; assert no silently missing enriched events.
3. **Make fraud counters honest.** Implement a genuine time-window structure and tests with timestamps spanning more than two hours, duplicates, out-of-order events and concurrent updates. Or rename the fields to their actual cumulative/TTL semantics.
4. **Make the experiment repeatable.** Record injection start/end and first/last observation times; use a single harness version and fixed model configuration, matched fault cases, no stale stack state, and traces for every run. Keep the free baseline and retrieval context from revealing the exact answer. Run multiple trials per fault. Have a human label a representative calibration set independently of the LLM judge.
5. **Regenerate and archive evidence.** Save raw ghz JSON, hardware/container versions, config, run commands, Kafka input/output counts, Prometheus snapshots, failures and test dates. Verify P99 and throughput on the entire path, including delivery. Publish only numbers that can be regenerated from those files.
6. **Add core service tests and a reproducible build.** Test dedup failure paths, producer delivery, invalid messages, GeoIP init errors and Redis window behavior. Arrange Go module paths so `go test ./...` works without Docker-specific copying, and run tests/Compose smoke checks in CI.

This audit did not rerun an LLM agent investigation or a live fault injection: the required model endpoint is external, the local stack was incomplete, and changing the running services would mix new work with the historical artifacts. The findings above distinguish source-level bugs from limits of the saved evidence.
